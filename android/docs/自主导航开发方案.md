# RobotCA Android 自主导航开发方案

> 当前状态更新：Android 端已经实现第一版 `SLAM 地图 A-B-A 往返导航 MVP`，包括 A/B 点选、free 栅格校验、`/move_base_simple/goal` 发布、`/move_base/status` 订阅、`/move_base/cancel` 取消和 A-B-A 状态机。下一阶段是在 APK 端实现多航点队列导航，小车端继续只跑 `move_base`。本文中关于“完整自主导航”的内容仍适用于后续稳定版，即保存地图后使用 `map_server + amcl + move_base`。

## 1. 背景

当前 RobotCA Android 项目已经具备遥控、激光雷达显示、相机显示、GPS 街道地图、SLAM 栅格地图显示和 A-B-A 往返导航 UI。完整稳定版 ROS 导航栈闭环仍需要实车验证和后续 AMCL/地图管理能力。

本方案目标分两层：

```text
第一层：在线 SLAM + move_base + Android A-B-A 往返验证
第二层：保存地图 + map_server + amcl + move_base 的稳定自主导航
```

推荐路线：

```text
SLAM 建图
  -> 保存 map.pgm + map.yaml
  -> 机器人端加载 map_server + amcl + move_base
  -> Android 显示地图并发送导航目标
  -> 机器人自主规划路径并执行
```

## 2. 当前代码已有能力评估

结论：当前代码已经实现 Android 端 A-B-A 导航交互和 ROS 标准 `move_base` topic 集成；机器人端 `move_base` 也已准备配置，下一步是实车验证。完整稳定版的 AMCL、地图保存/加载和路径显示仍属于后续阶段。

## 2.1 已实现的部分

### 2.1.1 手动速度控制

`RobotController` 已经发布速度控制 topic：

```text
topic: /cmd_vel
type: geometry_msgs/Twist
```

相关能力：

- joystick 控制
- tilt 控制
- stop
- safemode 速度限制

这是机器人运动控制的基础能力。

### 2.1.2 传感器订阅

`RobotController` 当前已订阅：

```text
/scan          sensor_msgs/LaserScan
/odom          nav_msgs/Odometry
/pose          geometry_msgs/Pose
/navsat/fix    sensor_msgs/NavSatFix
/image_raw/compressed sensor_msgs/CompressedImage
/map           nav_msgs/OccupancyGrid
/move_base/status actionlib_msgs/GoalStatusArray
```

其中 `/scan` 和 `/odom` 被现有本地航点控制使用。

### 2.1.3 本地航点系统

当前代码中已有 waypoint 相关能力：

- `ControlApp` 保存 waypoint 列表
- `LaserScanRenderer` 支持在激光雷达页面通过手势添加、移动、删除 waypoint
- `IWaypointProvider` 提供当前目标点
- `SimpleWaypointPlan` 按 waypoint 方向发布 `/cmd_vel`
- `WaypointPlan` 使用激光雷达 potential field 做简单避障

相关文件：

```text
src/android_foo/control_app/src/main/java/com/robotca/ControlApp/Core/Plans/SimpleWaypointPlan.java
src/android_foo/control_app/src/main/java/com/robotca/ControlApp/Core/Plans/WaypointPlan.java
src/android_foo/control_app/src/main/java/com/robotca/ControlApp/Core/IWaypointProvider.java
src/android_foo/control_app/src/main/java/com/robotca/ControlApp/Layers/LaserScanRenderer.java
src/android_foo/control_app/src/main/java/com/robotca/ControlApp/ControlApp.java
```

### 2.1.4 现有航点控制的性质

现有 `SimpleWaypointPlan` 和 `WaypointPlan` 是 Android 本地控制算法：

```text
Android 计算方向/避障
  -> 发布 /cmd_vel
  -> 机器人执行速度
```

它们不依赖：

- `map_server`
- `amcl`
- `move_base`
- global planner
- local planner
- costmap

所以它们更适合短距离实验或演示，不适合作为可靠的室内全局自主导航方案。

## 2.2 尚未实现的部分

当前第一版 A-B-A 导航已经实现以下 ROS 标准导航能力：

```text
/map 订阅与 SLAM 地图显示
/move_base_simple/goal 发布
/move_base/status 订阅
/move_base/cancel 发布
导航目标点 UI
目标点 free 栅格校验

```

仍未实现或未纳入第一版范围：

```text
move_base action client
/amcl_pose 订阅
/move_base/NavfnROS/plan 或 global_plan 显示

地图列表管理
```

因此，如果目标只是“在当前 SLAM 地图白色区域内让小车从 A 到 B，再返回 A”，Android 端逻辑已经具备，下一步是实车验证。如果目标升级为“保存地图后的稳定自主导航”，还需要继续实现 AMCL、地图加载、初始位姿和路径显示。

## 3. 推荐架构

自主导航应由机器人端负责规划和执行，Android 端负责显示、交互和发送目标。

## 3.1 机器人端职责

机器人端运行 ROS 导航栈：

```text
map_server
amcl
move_base
global_costmap
local_costmap
global_planner
local_planner
sensor/laser layer
```

机器人端负责：

- 加载保存好的地图
- 根据激光雷达和里程计定位
- 根据目标点规划路径
- 实时避障
- 控制底盘速度

## 3.2 Android 端职责

Android 端负责：

- 显示 `/map`
- 在地图上点选 A/B
- 显示 A/B 目标点
- 发布目标到 `/move_base_simple/goal`
- 显示导航状态
- 取消导航
- 后续可管理地图文件

当前第一版还未显示机器人在 `map` frame 下的当前位置，主要依赖地图上的 A/B 标记和 `/move_base/status` 做验证。

Android 端不应承担全局路径规划和底层运动控制。

## 4. 目标 ROS 接口

## 4.1 Android 需要发布

### 导航目标

```text
topic: /move_base_simple/goal
type: geometry_msgs/PoseStamped
frame_id: map
```

用途：

- 用户在 Android 地图上点击目标点
- Android 将屏幕坐标转换成 `map` 坐标
- 发布 `PoseStamped`
- `move_base` 接收并开始导航

### 取消目标

推荐使用 action cancel：

```text
topic: /move_base/cancel
type: actionlib_msgs/GoalID
```

第一版也可以仅提供 `STOP`，即停止 Android 侧控制或发送零速度，但这不能等价取消 `move_base` 目标。

## 4.2 Android 需要订阅

### 地图

```text
topic: /map
type: nav_msgs/OccupancyGrid
```

来自前置 `SLAM Map` 阶段。

### 机器人定位

推荐：

```text
topic: /amcl_pose
type: geometry_msgs/PoseWithCovarianceStamped
frame_id: map
```

用途：

- 在地图上显示机器人当前位置
- 校验机器人是否已经完成定位
- 导航目标需要基于同一 `map` frame

### 导航状态

```text
topic: /move_base/status
type: actionlib_msgs/GoalStatusArray
```

用途：

- 显示 Pending / Active / Succeeded / Aborted
- 判断目标是否到达

### 全局路径

常见 topic 之一：

```text
topic: /move_base/NavfnROS/plan
type: nav_msgs/Path
```

或：

```text
topic: /move_base/GlobalPlanner/plan
type: nav_msgs/Path
```

具体 topic 取决于 move_base 配置。

用途：

- 在地图上显示规划路径
- 辅助调试导航是否正常

### UI 模式


### 坐标转换

屏幕坐标转换为 OccupancyGrid 坐标：

```text
screen -> view local -> map pixel -> map meter
```

核心公式：

```text
map_x = origin_x + grid_x * resolution
map_y = origin_y + grid_y * resolution
```

注意：

- Android Canvas Y 轴向下
- OccupancyGrid 通常按左下原点理解
- Bitmap 生成时如果做了 Y 轴翻转，反算坐标时必须同步

### 目标朝向

第一版可以简化：

- 点击目标点：设置目标位置
- 长按或二次拖动：设置目标朝向

更简化的第一版：

- 目标朝向默认 `yaw = 0`
- 后续再加箭头调整

## 6. 与现有航点控制的关系

现有 `SimpleWaypointPlan` / `WaypointPlan` 可以保留，但不建议作为主导航方案。

推荐定位：

| 功能 | 保留方式 | 用途 |
|---|---|---|
| SimpleWaypoint | 保留 | 近距离测试、教学演示 |
| Waypoint potential field | 保留 | 简单避障实验 |
| move_base navigation | 新增主线 | 正式自主导航 |

原因：

- 现有航点控制没有全局地图
- 没有全局路径规划
- 没有 costmap
- 没有 AMCL 定位
- Android 端承担控制闭环，网络抖动会影响运动稳定性

正式导航应让机器人端 `move_base` 控制底盘。

## 10. 结论

当前代码已经实现了第一版 A-B-A 导航相关能力：

- `/map` 显示
- A/B 点选和显示
- free 栅格目标点校验
- `/move_base_simple/goal` 发布
- `/move_base/status` 订阅
- `/move_base/cancel` 发布
- A-B-A 状态机

但这些还不是完整稳定版自主导航。

稳定版 A 点到 B 点自主导航应基于：

```text
map_server + amcl + move_base
```

Android 端的最佳职责是：

```text
显示地图 + 显示定位 + 点选目标 + 发布 goal + 显示状态 + 取消导航
```

不要让 Android 端承担全局路径规划和运动控制闭环。

## 11. 2026-06-11 实车验证记录

今日已经完成第一轮 A-B-A 导航实车验证，结论如下：

- 机器人端 ROS 栈正常，`android_stack.sh start` 可启动 roscore、xtark bringup、gmapping、move_base。
- Android App 已连接 ROS master，节点为 `/android/robot_controller`。
- `/map`、`/scan`、`/odom`、`/move_base/status`、`/move_base_simple/goal` 链路正常。
- `/robot_pose_in_map` 已在机器人端发布，频率约 10Hz，Android 端具备车标显示链路。
- Android 发 goal 后，move_base 能接收目标并返回 `status=3`，即 `Goal reached`。
- A-B-A 核心链路已打通，当前阶段从“功能实现”进入“实车调参和稳定性优化”。

本次发现的问题：

| 问题 | 表现 | 当前判断 |
|---|---|---|
| 在线 gmapping 位姿跳变 | 路线看起来绕、抖、重画 | 在线 SLAM 小空间边建边导航的典型问题 |
| goal yaw 固定为 0 | 到点前可能原地转或走弧线 | 后续改为当前车头朝向或 A->B 方向 |
| `/cmd_vel` 双发布者 | move_base 和 Android 同时可发布速度 | 后续应在导航期间锁定 Android 手动速度输出 |
| 手动按钮方向 | 左移/左转曾与车头方向不一致 | 已修正手动按钮符号，保留 RobotController 既有全局取反逻辑 |
| 路径不可视化 | 点“去 B/返回 A”后看不到规划线 | 明日按《导航路径可视化开发方案.md》实现 |

当前优先级：

```text
1. 多次重复测试 A-B-A，不在导航期间碰摇杆
2. 实现 move_base 全局路径可视化
3. 导航期间禁止 Android 抢 /cmd_vel
4. goal yaw 使用当前车头朝向或目标方向
5. 稳定后再切换 保存地图 + map_server + amcl
```

注意：设 A/B 只是在 App 内保存点并画标记，不会触发规划。只有点击 `去 B`、`返回 A` 或 `A-B-A` 后，move_base 才会收到 goal 并开始规划。规划路径不是一次定死，行驶过程中会随 `/map`、`/scan`、TF 和 costmap 更新而重规划。

## 12. 2026-06-13 多航点队列导航方案

### 12.1 结论

多航点导航可行，建议在 Android APK 内实现，不改小车端。

核心链路：

```text
Android 维护航点队列
  -> 顺序调用 RobotController.publishMoveBaseGoal()
  -> move_base 逐个规划并发布 /cmd_vel
  -> Android 监听 /move_base/status
  -> SUCCEEDED 后推进到下一个航点
```

小车端继续保持当前职责：

```text
android_stack.sh
```

### 12.2 边界

本阶段只做“已走过 SLAM 地图上的多航点顺序导航验证”：

- 目标点必须在 Android 当前 `/map` 的 free 区域内。
- 每个航点仍然通过 `/move_base_simple/goal` 交给 move_base。
- 避障、局部规划、速度输出仍然由机器人端 move_base 负责。
- Android 不自己算全局路径，不直接按多点路径发 `/cmd_vel`。
- 在线 gmapping 地图跳变导致的重规划、路径重画属于当前阶段可接受现象。

暂不做：

- 保存地图后的 AMCL 稳定导航。
- 多地图航点管理。
- 云端/Redis/后端任务系统。
- 复杂任务编排、条件分支、自动充电。

### 12.3 数据模型

第一版使用简单 POJO，先内存验证，稳定后再持久化。

```java
class Waypoint {
    String name;   // "1" / "2" / "充电点"
    double x;
    double y;
    double yaw;    // 第一版固定 0.0，后续再支持朝向

enum MissionState {
    IDLE,
    RUNNING,
    PAUSED,
    FINISHED,
    FAILED,
    CANCELED
}

class WaypointMission {

    int currentIndex;
    boolean loop;
    MissionState state;
}
```

```text
SharedPreferences 或 JSON
  -> 按当前地图名 / 任务名保存
  -> 支持导入导出
```

### 12.4 执行层设计

新增 `MoveBaseMissionRunner`，不要继续把任务调度塞进 `SlamMapFragment`。

建议文件：

```text
android/.../Core/Waypoint.java
android/.../Core/WaypointMission.java
android/.../Core/MoveBaseMissionRunner.java
```

职责：

| 方法 | 职责 |
|---|---|
| `start(mission)` | 校验任务，发送第一个航点 |
| `onStatus(GoalStatusArray)` | 消费 `/move_base/status`，判断当前 goal 成败 |
| `advance()` | 当前点成功后推进到下一个点 |
| `pause()` | 取消当前 move_base goal，保留 `currentIndex` |
| `resume()` | 重新发送当前 `currentIndex` 对应航点 |
| `stop()` | 取消当前 goal，并将任务置为 `CANCELED` |

状态机：

```text
IDLE
  -> start()
  -> RUNNING / WAITING_ACTIVE
  -> 看到 PENDING 或 ACTIVE
  -> RUNNING / ACTIVE_SEEN
  -> SUCCEEDED
  -> advance()
      -> 有下一个点：继续 RUNNING / WAITING_ACTIVE
      -> 没有下一个点：FINISHED

RUNNING
  -> ABORTED / REJECTED
  -> FAILED

RUNNING
  -> PREEMPTED 或 stop()
  -> CANCELED

RUNNING
  -> pause()
  -> PAUSED
```

必须保留当前 A/B 逻辑里已有的防误判策略：

```text
发 goal 后，不能立刻相信 SUCCEEDED。
必须先看到该 goal 进入 PENDING 或 ACTIVE，
然后才允许把 SUCCEEDED 当作“当前目标完成”。
```

原因：`/move_base/status` 可能短时间内还带着上一个 goal 的完成状态，直接判断 `SUCCEEDED` 会导致新航点被跳过。

### 12.5 与现有 A/B 的关系

保留 A/B 作为快捷验证入口，多航点作为旁路新增。

```text
A/B 模式：
  继续使用现有 去 B / 返回 A / A-B-A

多航点模式：
  使用 List<Waypoint> + MoveBaseMissionRunner
```

短期不强行统一两套 UI，避免破坏已经跑通的 A/B 往返验证。

后续如果多航点稳定，再考虑把 A/B 也变成 mission 的两个特殊航点：

```text
A-B-A = [B, A]
```

### 12.8 风险与处理

| 风险 | 表现 | 处理 |
|---|---|---|
| 旧 goal status 误判 | 新航点刚发出就被认为成功 | Runner 必须等待 PENDING/ACTIVE 后才接受 SUCCEEDED |
| 在线 SLAM 地图跳变 | 路径线重画、路线突然变化 | 当前阶段接受，调试时慢速跑图 |
| 航点靠近障碍 | move_base 拒绝或绕路失败 | 复用 free 栅格 + 半径校验 |
| Android 仍能手动发 `/cmd_vel` | 导航轨迹偏离规划 | 下周实现前先操作约束，后续加导航期间手动锁定 |
| 多点 UI 过复杂 | 实现慢、难验证 | P1 只做添加、清空、开始、停止 |
| 任务持久化与地图不匹配 | 换地图后航点坐标失效 | P2/P3 按地图名保存，第一版先提示风险 |

### 12.9 不采用的方案

不采用 Redis + 小车端多目标监听：

- 多一层服务，部署复杂。
- 当前离线包和前端不完整。
- 与 Android 直连 move_base 的调试链路不一致。

不采用 Android 本地 `SimpleWaypointPlan`：

- 它直接发 `/cmd_vel`，绕开 move_base。
- 不使用全局 costmap、局部 costmap 和标准恢复机制。
- 不适合当前“SLAM 地图上两点/多点导航”的主线。

不在小车端写新的队列节点：

- 当前手机控车场景下，任务编辑和调试都在 APK 端更直观。
- 小车端只负责稳定运行 ROS 导航栈，职责更清楚。
