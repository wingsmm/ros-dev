# Xtark 激光里程计实验方案

## 0. Current execution rule: avoid extra stop

Nano boot does not auto-start any stack. All stacks are started explicitly by script commands.

Cold boot / known-clean flow:

```bash
qt_stack.sh start
qt_stack.sh record
# Qt connect 192.168.1.168:8765 and drive slowly.
# Qt camera preview: http://192.168.1.168:8080/stream?topic=/camera/image_raw
qt_stack.sh stop
```

Do not run extra `android_stack.sh stop` in a known-clean boot when only Qt is needed.

Use cleanup only when you are unsure whether another stack was started earlier:

```bash
android_stack.sh stop
qt_stack.sh stop
qt_stack.sh start
```

Stack boundary:

- `qt_stack.sh` owns the Qt daily stack: `roscore + xtark_bringup + JSON :8765 + Qt camera preview + rf2o` (+ optional `record` rosbag).
- `qt_stack.sh stop` only stops PIDs recorded by this stack.
- `android_stack.sh` is the separate Android full stack (SLAM + navigation).
- The two stacks are mutually exclusive (`stack_common.sh` owner + process checks).
- Set `CAMERA_ENABLE=0` or `LASER_ODOM_ENABLE=0` for lightweight Qt runs.

Script modes:

| Script | Mode |
|------|------|
| `laser_odom_experiment.sh` | Sidecar only: starts rf2o and assumes bringup plus `/scan` already exist |
| `qt_stack.sh` | Complete Qt stack (recommended for field compare + Qt 里程计对照页) |

> 历史 bag 路径可能仍为 `~/xtark_logs/laser_odom_compare/`；新录包在 `~/xtark_logs/qt_stack/bags/`。

整理日期：2026-06-18

本文说明一个**实验方案**：使用现有 2D 激光雷达 `/scan` 估算里程计，生成 `/odom_laser`，用于对比或后续替代轮子里程计。

结论先行：

```text
方案可行，但不要一上来替换主线 /odom。
先并行跑 /odom_laser，对比稳定性，再决定是否接入 gmapping / move_base。
```

## 1. 背景

当前 bringup 的里程计链路不是单一数据源：

```text
OpenCTR / STM32 下位机
  -> 编码器里程计反馈帧
  -> xtark_driver
  -> /odom_raw

/odom_raw + /imu
  -> robot_pose_ekf
  -> /odom
```

因此 `/odom_raw` 才是编码器原始里程计，`/odom` 是编码器与 IMU 的融合位姿。
这条链路的优点是频率高、与底盘控制一致；缺点是麦克纳姆轮容易受打滑、地面摩擦、横移误差影响。

激光里程计的思路是：

```text
/scan 前后两帧
  -> 激光扫描匹配
  -> 估算 dx / dy / dyaw
  -> 发布 /odom_laser
```

它不需要新增硬件，使用当前 RPLidar 的 `/scan` 即可先试。

---

## 2. 目标

第一阶段目标不是替换主线，而是做对照实验：

```text
编码器原始里程计：/odom_raw
编码器 + IMU 融合：/odom
激光里程计：/odom_laser
```

对比内容：

| 对比项 | 说明 |
|--------|------|
| 直线前进 | `/odom` 和 `/odom_laser` 的 x 是否一致 |
| 原地旋转 | yaw 是否稳定、是否漂移 |
| 横移 | 麦轮横移时 `/odom_laser` 与 `/odom_raw`、`/odom` 的差异 |
| 静止 | 车不动时 `/odom_laser` 是否抖动 |
| 环境变化 | 有人走动、长走廊、大空场时是否失稳 |

## 3. 推荐实现

推荐先使用 `rf2o_laser_odometry` 这类 ROS1 激光里程计节点。

仓库已提供独立实验包（**不碰主线**）：

```text
xtark/xtark_laser_odometry/
  launch/rf2o_odom_laser.launch
  config/rf2o_laser_odometry.yaml
  README.md
```

轻量启停脚本（可选，不并入正式 `qt_stack.sh` / `android_stack.sh`）：

```text
xtark/scripts/laser_odom_experiment.sh   # 仅 rf2o 旁路
xtark/scripts/qt_stack.sh                # Qt 全栈 + rosbag record（推荐现场测）
```

**现场对照**：以第 0 节为准；冷启动或确认无其它栈运行时，不要额外执行 `android_stack.sh stop`。

```bash
qt_stack.sh start
qt_stack.sh record
# Qt 192.168.1.168:8765 低速控车
qt_stack.sh stop
```

每个脚本只有：`start | stop | record | logs`，不互相调用。

部署到机器人后：

```bash
cd ~/ros_ws && catkin_make && source devel/setup.bash
roslaunch xtark_laser_odometry rf2o_odom_laser.launch
# 或
~/ros_ws/scripts/laser_odom_experiment.sh start
```

建议话题规划：

| 数据 | 话题 |
|------|------|
| 激光输入 | `/scan` |
| 编码器原始里程计 | `/odom_raw` |
| 编码器 + IMU 融合 | `/odom` |
| 激光里程计 | `/odom_laser` |
| 激光里程计 TF | 实验阶段建议先关闭或单独隔离 |

不要直接让激光里程计发布成 `/odom`，避免覆盖当前主线。

## 5. 接入顺序

### 阶段一：并行观察

只新增 `/odom_laser`，不改 gmapping、move_base、Android、Qt。

验收标准：

| 项 | 标准 |
|----|------|
| 节点稳定 | `/odom_laser` 持续发布 |
| 静止稳定 | 静止时 x/y/yaw 不明显漂移 |
| 运动合理 | 前进、旋转、横移趋势正确 |
| 不影响主线 | `/odom`、`/scan`、Android、Qt 原功能不变 |

### 阶段二：让 gmapping 试用

如果 `/odom_laser` 表现稳定，可以单独开一套实验 launch，让 gmapping 使用激光里程计。

注意：

- 不要改现有主线 launch。
- 使用新 launch 或参数开关。
- 保留回退到 `/odom` 的方式。

### 阶段三：再考虑 move_base

move_base 对 odom 稳定性要求更高，不建议第一步就切。

只有在以下条件满足后再试：

| 条件 | 说明 |
|------|------|
| `/odom_laser` 静止不漂 | 不然局部规划会抖 |
| 旋转方向正确 | yaw 正负方向不能反 |
| TF 链完整 | `odom -> base_footprint` 或等效链路清晰 |
| 可快速回退 | 出问题能立刻切回主线融合 `/odom` |

## 6. 优点和风险

优点：

| 优点 | 说明 |
|------|------|
| 不新增硬件 | 当前 2D 雷达即可试 |
| 可减轻轮子打滑影响 | 运动估计来自环境匹配 |
| 适合作为对照 | 可判断轮子 odom 是否明显漂 |

风险：

| 风险 | 说明 |
|------|------|
| 环境依赖强 | 墙、桌腿、固定障碍越多越稳 |
| 长走廊可能退化 | 几何特征少，匹配容易漂 |
| 大空场可能不稳 | 激光可见结构不足 |
| 动态物体影响 | 人、椅子移动会干扰匹配 |
| TF 容易冲突 | 不能同时有两个节点抢发同一条 odom TF |

---

## 7. 和 IMU / 编码器的关系

本实验不是取消底盘控制，也不是不用编码器。

| 数据 | 当前作用 |
|------|----------|
| `/cmd_vel` | 仍然控制底盘 |
| `/odom_raw` | 轮子编码器原始里程计 |
| `/odom` | 编码器与 IMU 融合结果，主线继续保留 |
| `/odom_laser` | 激光里程计实验输出 |
| `/imu` | 当前 bringup 中参与 `robot_pose_ekf`，并非只读取显示 |

如果后续要把激光也纳入融合，应另开实验配置，不覆盖当前 `/odom`：

```text
/odom_raw    轮子编码器原始里程计
/odom_laser  激光里程计
/imu         IMU
  -> robot_localization / EKF
  -> /odom_fused
```

但这属于后续阶段，不建议和第一轮实验混在一起。

---

## 8. 不要做什么

- 不要一开始就把 `/odom_laser` remap 成 `/odom`。
- 不要直接改主线 bringup / gmapping / move_base launch。
- 不要让两个节点同时发布同一条 `odom -> base_footprint` TF。
- 不要把激光里程计写成“必然优于轮子里程计”。
- 不要在大空场或动态人群环境下直接下结论。

#### 9.3.2 横移现场观察与数据解释

现场观察：麦克纳姆轮执行左移、右移时，车体没有保持纯 90° 横移，而是先向斜后方
移动，再沿近似原路返回。

以 `x` 为车体前后方向、`y` 为左右方向，激光数据为：

| 动作 | 激光位移 `(dx, dy)` | 路程 | 相对纯横移偏角 |
|------|----------------------|------|----------------|
| 左移 | `(-0.243, +0.354) m` | 0.429 m | 约 34°，左后方斜移 |
| 右移 | `(+0.253, -0.348) m` | 0.430 m | 约 36°，右前方返回 |

两段激光向量相加：

```text
dx ≈ +0.010 m
dy ≈ +0.006 m
净偏移约 0.012 m
```

这与“斜向移动后近似原路返回”的现场观察一致。此前把 0.43 m 解释为“激光横移少算”
并不成立，应撤回该判断。

编码器与融合里程计仍按理想麦克纳姆轮运动学解释轮子转动：

| 动作 | `/odom_raw` | 融合 `/odom` |
|------|-------------|--------------|
| 左移 | `(-0.005, +0.605) m` | `(-0.024, +0.602) m` |
| 右移 | `(+0.053, -0.655) m` | `(+0.086, -0.649) m` |

因此本次横移差异更可能说明：**真实车体发生斜行或打滑，而编码器仍报告理想横移**。
激光里程计在这里提供了有价值的独立环境观测，不能把 `/odom_raw` 或 `/odom` 直接当作
横移真值。

右移段还出现约 5.8°（融合）和 6.4°（激光）的 yaw 变化，进一步支持车体运动发生变形；
是否属于机械执行问题，需要结合四轮目标/反馈和现场车体朝向判断。

#### 9.3.3 第一次测试结论

| 项 | 结论 |
|----|------|
| 数据采集与 HTML 报告 | **通过** |
| 前进/后退对照 | **通过**，激光与融合累计距离接近 |
| 左右横移 | 激光数据与现场斜行、近似原路返回的观察一致 |

全程激光相对融合 `/odom` 的平面 RMSE 约 9.7 cm、yaw RMSE 约 3.2°；这些数值是
估计器之间的一致性差异，不是相对真实运动的绝对精度。

### 9.4 第二次专项测试：左转与右转（待执行）

每段动作前后静止 3～5 秒，并使用地砖缝或长直线检查车体最终朝向。验收时分别比较
`/odom_raw`、融合 `/odom`、`/odom_laser` 的 yaw，不与第一次横移结论混合。
