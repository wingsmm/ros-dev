# 宇树 L1 对接方案

本文是本仓库里 Unitree / 宇树 L1 雷达落地的主入口。以后讨论 L1 接入、cockpit 可视化、TF、Point-LIO、避障消费时，以本文为准；其它文档只作为资料或历史记录。

## 一句话结论

当前正确落地路径是：

```text
Jetson 跑官方 unitree_lidar_ros2
  -> 发布 /unilidar/cloud + /unilidar/imu
  -> VMware/VM 观测端通过同一 ROS_DOMAIN_ID 订阅
  -> RViz2 先用 Fixed Frame=unilidar_lidar 看原始点云
  -> 原始链路稳定后，再加 base_link 静态 TF
  -> 最后再接 Point-LIO / odom / 避障
```

不要一上来把官方驱动、TF、Point-LIO、odom adapter、cockpit 一键启停绑成一个大栈。先把官方原始点云闭环跑稳。

## 分阶段落地

### 阶段 1：官方原始点云闭环

目标：只证明 L1 官方驱动在 Jetson 上能稳定发布原始点云，VMware/VM 观测端能看见。

链路：

```text
Jetson unitree_lidar_ros2
  -> /unilidar/cloud   sensor_msgs/PointCloud2, frame=unilidar_lidar
  -> /unilidar/imu     sensor_msgs/Imu, frame=unilidar_imu

VMware/VM RViz2
  -> Fixed Frame=unilidar_lidar
  -> PointCloud2=/unilidar/cloud
```

要做：

1. 在 Jetson 上固定串口别名为 `/dev/unilidar_lidar`。
2. 将官方 launch 中的串口路径改为 `/dev/unilidar_lidar`。
3. 在 Jetson 上编译 `unitree_lidar_ros2` 和 `unitree_lidar_sdk`。
4. 在 Jetson 上直接 `ros2 launch unitree_lidar_ros2 launch.py`。
5. 在 VMware/VM 观测端上用同一个 `ROS_DOMAIN_ID` 查 topic 和打开 RViz。

验收：

- Jetson 上雷达节点无串口权限错误。
- VMware/VM 观测端能看到 `/unilidar/cloud` 和 `/unilidar/imu`。
- `/unilidar/cloud` 频率接近 9 Hz。
- `/unilidar/imu` 高频稳定。
- RViz 中点云可见，遮挡雷达时点云变化。

建议命令：

```bash
# Jetson
cd ~/qt/ros2_ws
source /opt/ros/humble/setup.bash
colcon build --packages-select unitree_lidar_ros2 unitree_lidar_sdk
source install/setup.bash
ros2 launch unitree_lidar_ros2 launch.py
```

```bash
# VMware/VM 观测端
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=0
ros2 topic list
timeout 12 ros2 topic hz /unilidar/cloud
timeout 12 ros2 topic hz /unilidar/imu

cd jetson/cockpit
bash scripts/start_unilidar_rviz.sh
```

## 阶段 2：接入车体 TF

目标：把雷达坐标系挂到车体坐标系，但不引入 SLAM。

目标 TF：

```text
base_link
  -> unilidar_lidar
  -> unilidar_imu
```

原则：

- 先用 RViz 看 `unilidar_lidar` 的 X/Y/Z 轴，确认实车安装方向。
- 卧放安装时，如果 Z 轴朝前，只在静态 TF 里修正，不改驱动 topic 和 frame 名称。
- `base_link -> unilidar_lidar` 的平移来自实车测量。
- `unilidar_lidar -> unilidar_imu` 只有在确认官方外参或项目需要时再发布，不要猜。

验收：

- `tf2_echo base_link unilidar_lidar` 有稳定输出。
- RViz `Fixed Frame=base_link` 时仍能看到原始点云。
- 点云前后左右与车体方向一致。

### RViz 配置（三模式，勿混用）

| 模式 | 配置文件 | Fixed Frame | PointCloud2 topic | 阶段 |
|------|----------|-------------|-------------------|------|
| 原始点云 | `config/unilidar.rviz` | `unilidar_lidar` | `/unilidar/cloud` | 1 |
| 车体对齐 | `config/unilidar_base.rviz` | `base_link` | `/unilidar/cloud_aligned` | 2 |
| 雷达里程计 | `config/unilidar_mapping.rviz` | `camera_init` | `/cloud_registered` | 3a |

cockpit `lidar_panel` 已提供上述三档单选；Qt 只负责打开对应 RViz 配置，**不证明外参正确**。

`/unilidar/cloud_aligned` 是传感器点云流，`l1_cloud_align` 按
`SensorDataQoS` 发布（Best Effort）。因此 `config/unilidar_base.rviz`
里的 PointCloud2 Display 必须设置：

```text
Topic: /unilidar/cloud_aligned
Reliability Policy: Best Effort
```

如果误设为 `Reliable`，原始点云仍会正常显示，但车体对齐视图会空白。
VM RViz 日志会出现：

```text
New publisher discovered on topic '/unilidar/cloud_aligned',
offering incompatible QoS.
Last incompatible policy: RELIABILITY_QOS_POLICY
```

这种情况不代表 `l1_cloud_align` 没启动；应优先检查 RViz QoS 配置。

阶段二起，「车体对齐」不再靠改 `base_link -> unilidar_lidar` 静态 TF 的 rpy 假装旋转，而是由 `l1_cloud_align` 节点做真正的 `PointCloud2` 刚体变换：

```text
/unilidar/cloud (frame=unilidar_lidar)
  -> l1_cloud_align_node
  -> /unilidar/cloud_aligned (frame=base_link)
```

`l1_cloud_align` 里有两层旋转，必须分清：

```text
R_base_lidar = R(base_rpy_rad)     # 安装基准：L1 原始坐标 -> base_link
R_trim_base  = R(trim_rpy_rad)     # 现场微调：绕 base_link 车体轴
R_final      = R_trim_base * R_base_lidar
```

当前实车卧放基准：

```text
lidar +Z -> base_link +X  （车头）
lidar +X -> base_link +Z  （朝上）
lidar +Y -> base_link -Y  （车右）
base_rpy_rad = [pi, -pi/2, 0]
```

`base_rpy_rad` 是安装事实，不是现场调平旋钮；UI 不应该暴露它。现场窗口只调
`trim_rpy_rad`，给人的文案是：

```text
roll（左右歪，先调这个）
pitch（前后翘，再调这个）
yaw（车头方向偏，最后调）
```

现场已验证：楼顶/地面这类整体侧倾，优先调 `roll`；当前调到约 `25°`
时画面明显更平。`pitch` 只在前后方向还翘时微调，`yaw` 只在水平车头
方向不对时再动。这里调的是点云整体，不是 RViz 坐标轴显示。

### 观测端与启动（VMware）

阶段二验收在 VMware 上做；它是 cockpit/RViz 当前唯一支持的观测环境。

Jetson（TF + 点云对齐发布端）：

```bash
cd ~/qt/ros2_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=0

# L1 驱动（阶段一，若未在跑）
ros2 launch unitree_lidar_ros2 launch.py

# 静态 TF —— 只保证坐标树存在，不再作视觉调平
ros2 launch l1_tf_bringup l1_static_tf.launch.py \
  extrinsics_yaml:=~/qt/ros2_ws/src/l1_tf_bringup/config/l1_extrinsics.yaml

# 点云对齐 —— 真正旋转点云并发布到 /unilidar/cloud_aligned
ros2 launch l1_cloud_align l1_cloud_align.launch.py \
  align_yaml:=~/qt/ros2_ws/src/l1_cloud_align/config/l1_cloud_align.yaml
```

`l1_extrinsics.yaml`（**只给静态 TF 用，不做视觉调平**）：

```yaml
xyz: [0.0, 0.0, 0.0]
base_rpy_rad: [3.14159265359, -1.57079632679, 0.0]   # 卧放基准（弧度）
trim_rpy_rad: [0.0, 0.0, 0.0]                        # 保留字段；勿滥用作视觉调平
```

`l1_cloud_align.yaml`（**点云视觉对齐的真源**，cockpit 「点云对齐」窗口读写此文件）：

```yaml
input_topic: /unilidar/cloud
output_topic: /unilidar/cloud_aligned
target_frame: base_link

xyz: [0.0, 0.0, 0.0]
base_rpy_rad: [3.14159265359, -1.57079632679, 0.0]   # 卧放基准（弧度，不由 UI 改）
trim_rpy_rad: [0.0, 0.0, 0.0]                         # 车体系微调（弧度，UI 输入度）
```

节点内部按 `R_final = R(trim_rpy_rad) * R(base_rpy_rad)` 组合，`p_out = R_final * p_in + xyz`：
先把 L1 原始坐标转到 base_link，再在 base_link 系里做现场微调，
所以 UI 里的 roll/pitch/yaw 才是真正“绕 RViz 红/绿/蓝轴”。

调参顺序（在 cockpit 的「点云对齐」窗口里做，参数写进 `l1_cloud_align.yaml` 的 `trim_rpy_rad`）：

- 地面/楼顶左右倾斜 → 先调 `trim_rpy_rad[0]` **roll**（绕 `base_link +X`，红轴）
- 前后俯仰不平 → 调 `trim_rpy_rad[1]` **pitch**（绕 `base_link +Y`，绿轴）
- 水平车头方向错 → 调 `trim_rpy_rad[2]` **yaw**（绕 `base_link +Z`，蓝轴）
- 点云整体前后左右偏、姿态已平 → `xyz[0/1/2]`（米）

`base_rpy_rad` 是安装基准，读取后由 cockpit 缓存并原样写回；读取失败时应用按钮会直接失败提示，不会用零值覆盖 Jetson 上已确认的基准。

cockpit 阶段二闭环：VM Qt 通过 ssh 直连 Jetson（`JETSON_SSH_*`）：

```text
启动雷达（l1_stack.sh start，幂等：L1 + static TF + l1_cloud_align）
  -> 打开雷达视图（cloud 有 publisher；车体对齐再看 /unilidar/cloud_aligned）
  -> 点云对齐 / 应用对齐参数（写 l1_cloud_align.yaml + 仅 restart l1_cloud_align）
  -> 停止雷达（停 L1 + static TF + l1_cloud_align）
```

不向用户暴露 TF 启停按钮，也不因为改点云对齐而重启 L1 驱动 / static TF。

状态判断边界：

- 原始点云模式：主判断是 `/unilidar/cloud` 有 publisher；Hz 采样只是辅助显示。
- 车体对齐模式：主判断是 `/unilidar/cloud_aligned` 有 publisher，RViz 订阅它并固定到 `base_link`。
- `base_link -> unilidar_lidar` 静态 TF 缺失只影响 RViz 的坐标轴/TF 辅助显示；不应把它当成 `/unilidar/cloud_aligned` 不可用。
- 如果 `l1_stack.sh` 显示 `aligned=yes` 但车体对齐 RViz 空白，优先检查 `unilidar_base.rviz` 的 PointCloud2 QoS 是否是 `Best Effort`。

首次把 `l1_stack.sh` / `l1_static_tf.sh` / `l1_cloud_align.sh` + 新增 `l1_cloud_align` 包同步到 Jetson：

```bash
bash jetson/scripts/jetson.sh ros2 push --yes
# 在 Jetson 上编译：cd ~/qt/ros2_ws && colcon build --packages-select l1_cloud_align
```

`l1_stack.sh stop` / `l1_static_tf.sh stop` / `l1_cloud_align.sh stop` 会结束各自进程；调试期间**不要同时手工另起同 child frame 的 static TF 或同名 align 节点**，否则 stop 会一并清掉。

`child` 必须等于 `/unilidar/cloud` 的 `header.frame_id`（当前为 `unilidar_lidar`）。

VM（观测端）：

ros2 run tf2_ros tf2_echo base_link unilidar_lidar

## 阶段 3a：Point-LIO 原始闭环

目标：用官方 Point-LIO 把 L1 自带点云 + IMU 跑成可见轨迹，不做复杂架构。

链路：

```text
unitree_lidar_ros2
  -> /unilidar/cloud
  -> /unilidar/imu

point_lio
  -> /aft_mapped_to_init   (nav_msgs/Odometry, frame: camera_init -> aft_mapped)
  -> /cloud_registered     (sensor_msgs/PointCloud2)
  -> /path                 (nav_msgs/Path)
  -> TF: camera_init -> aft_mapped
```

使用链路（只接官方 Point-LIO 最小闭环，不碰阶段二点云对齐逻辑）：

- 不把 `/unilidar/cloud_aligned` 喂给 Point-LIO。
- 不把阶段二 `l1_cloud_align` 和 Point-LIO 混在一起。
- `mapping_unilidar_l1.launch.py` 的 Node 参数当前显式设置 `use_imu_as_input: false`。L1 自带 IMU 仍由 `unilidar_l1.yaml` 的 `imu_en: true` 接入；这里先走 Point-LIO 的 `kf_output` 路径做阶段 3a 验证。
- `unilidar_l1.yaml` 的 `publish_odometry_without_downsample` 当前必须保持 `false`，避免 `/aft_mapped_to_init` 和 `/tf` 高频发布把 VMware/WiFi 的 DDS 链路打满。
- 不做 `odom -> base_link` adapter。
- 不做 Qt 一键化，先证明 LIO 能跑。

### 当前验证参数（2026-07-13，已验证）

本阶段先以“能稳定发布 odom/path/tf”为目标，参数取保守值：

```text
mapping_unilidar_l1.launch.py:
  use_imu_as_input = false

unilidar_l1.yaml:
  mapping.imu_en = true
  mapping.imu_time_inte = 0.004
  odometry.publish_odometry_without_downsample = false
```

说明：

- `imu_en=true` 表示 L1 自带 IMU 仍然参与 Point-LIO。
- `use_imu_as_input=false` 表示先走 `kf_output` 路径。之前 `true` / `kf_input` 路径下，`/cloud_registered` 能输出，但 `/aft_mapped_to_init`、`/path`、`/tf` 不更新，阶段 3a 验收卡住。
- `publish_odometry_without_downsample=false` 表示 odom/tf 按接近雷达帧频输出。之前高频输出模式会让 `/aft_mapped_to_init` 跑到很高频，VMware/WiFi DDS 观测容易堵塞。

如果后续要重新 A/B `use_imu_as_input=true`，必须先保留 `publish_odometry_without_downsample=false`，并用 topic 数据验证，不要只看 RViz 画面。

### 2026-07-13 复测结论：阶段 3a 数据链路通过

部署 `use_imu_as_input=false` + `publish_odometry_without_downsample=false` 后，Point-LIO 的里程计发布链路已恢复：

| 话题 | 复测结果 | 说明 |
|------|----------|------|
| `/cloud_registered` | ✅ ~8.8 Hz | 配准点云正常，VM 可收到 |
| `/aft_mapped_to_init` | ✅ ~8.7 Hz | `frame_id: camera_init`，VM 可收到 |

结论：

- `use_imu_as_input=false` 解决了上一轮 `/cloud_registered` 有数据但 odom/path/tf 不更新的问题。

- 阶段 3a 的 topic + VM RViz 目视闭环已通过；如果后续 RViz 显示混乱，先按下方 RViz 配置排查，不要再回滚 Point-LIO 参数。

### 失败排查顺序

1. `/unilidar/cloud` 不稳：先回阶段一。
2. `/unilidar/imu` 不稳：先查 L1 驱动，Point-LIO 不要继续调。

6. 轨迹方向奇怪：先记录，不要马上改算法；这是下一步外参/坐标统一问题。

2. `point_lio mapping_unilidar_l1.launch.py rviz:=false` — 正常，IMU 初始化 100%

**DDS 跨网络通信：**
- `/unilidar/cloud` ✅ VM 收到（~8.8 Hz）
- `/unilidar/imu` ✅ VM 收到（~247 Hz）
- `/cloud_registered` ✅ VM 收到，`frame_id: camera_init`
- `/aft_mapped_to_init` ⚠️ Topic 存在但 Jetson 和 VM 均收不到数据
- `/path` ⚠️ Topic 存在，仅有 1 初始帧（`sec:0`），之后不更新
- `/tf` ⚠️ Topic 存在但无数据

**已知问题：**

1. **KF 里程计未收敛（阻塞项）**
   - Point-LIO CPU 182%，`/cloud_registered` ~9 Hz 正常输出
   - 但 KF 内部 `update_iterated_dyn_share_modified()` 返回 false，`publish_odometry()` 始终不执行
   - `/path` 只有初始帧（`sec:0`），人工搬动 30cm 后未新增任何 pose
   - 疑似 `use_imu_as_input=True` / `kf_input` 模式下 KF 残差收敛条件过严
   - 当前处理：切到 `use_imu_as_input=False` / `kf_output` 后重新验收

2. **DDS 带宽瓶颈（非阻塞，需注意）**
   - `publish_odometry_without_downsample: true` 导致里程计按 IMU 频率（~250 Hz）以 RELIABLE QoS 发布
   - WiFi 链路下 RELIABLE 的 ACK 等待导致数据流堵死
   - `/cloud_registered`（~9 Hz，RELIABLE）能走通是因为频率低
   - 当前处理：`publish_odometry_without_downsample` 改 `false`，让里程计只随雷达帧（~9 Hz）发布

**当前结论：** 旧组合 `use_imu_as_input=True` + `publish_odometry_without_downsample=True` 会导致 KF 不收敛风险 + DDS 带宽超载风险。仓库当前已改成 `use_imu_as_input=False` + `publish_odometry_without_downsample=False`，并已复测确认 `/aft_mapped_to_init`、`/path`、`/tf` 恢复输出。

## 阶段 4：odom adapter + cockpit 一键化 LIO

目标：把 Point-LIO 的 `camera_init -> aft_mapped` 桥接到标准 ROS 导航格式，并经 cockpit 一键启停。

**状态（2026-07-14）**：代码已实现并部署；topic/TF 机上验收已通过；人工短距离搬动车体时，物理位移已能在 VMware RViz 中由 `/odom`、`/odom_path` 和配准点云连续显示，L1 定位观测闭环基本成立。**3～5 米定距、往返与底盘自主行走验收尚未完成**，因此暂不宣称达到导航级精度。

### 最终链路

```text
cockpit「雷达/里程计」→ 启动定位
  -> l1_stack：L1 驱动 + static TF + cloud_align
  -> Point-LIO（原始 /unilidar/cloud + /unilidar/imu）
  -> lio_odom_adapter
  -> /odom + /odom_path + TF odom->base_link
  -> RViz（Fixed Frame=odom）
```

TF 树：

```text
odom
├── camera_init          (static identity，由 adapter 发布)
│   └── aft_mapped       (Point-LIO 动态 TF)
└── base_link            (adapter 动态 TF)
    └── unilidar_lidar   (l1_static_tf)
        └── unilidar_imu (l1_static_tf)
```

### adapter 坐标变换

Point-LIO `/aft_mapped_to_init` 视为 `T_camera_init_imu`。`odom` 与 `camera_init` 原点重合。

```text
T_odom_base = T_camera_init_imu * inverse(T_base_imu)
```

其中 `T_base_imu` 由 TF `base_link -> unilidar_lidar -> unilidar_imu` 查询。

本阶段验收以 **pose / TF / `/odom_path`** 为准。`/odom.twist` 与 covariance 虽经 adjoint 转换，但 Point-LIO 原始 twist 参考系语义不够标准，**暂无真机速度对照证明，不得直接作导航控制输入**。

长期运行配置：

- Point-LIO 的 `pcd_save.pcd_save_en=false`。`interval=-1` 会把每帧点云累积在内存中直到退出，只在明确需要导出 PCD 的短时任务中临时开启。
- Point-LIO 的 `publish.path_en=false`。标准轨迹统一由 adapter 发布 `/odom_path`，避免重复发送无限增长的原始 `/path`。
- adapter 的 `max_path_length=1000`，约保留 L1 近两分钟轨迹，防止 RViz/DDS 因整条 Path 持续增大而变卡。

**禁止**把 `camera_init` 改名为 `odom`、把 `aft_mapped` 改名为 `base_link` 冒充车体适配；
**禁止**使用 `correct_odom_unilidar_l1.launch.py`；
**禁止**从 `/cmd_vel` 生成 odom；
**禁止**把 `/unilidar/cloud_aligned` 输入 Point-LIO。

## 阶段 5：底盘行走验收后接台阶识别与相机互补

### 启动条件

先让底盘能够稳定前进、后退和转向，再开始本阶段。底盘未恢复正常行走前，不继续堆叠识别、融合或导航代码。

### 下一步目标

1. 用真实底盘运动完成 3～5 米直行、往返和转向测试，记录距离误差、横向漂移与错误偏航。
2. 研究 L1 点云中的台阶几何特征，先区分“可通行缓坡 / 可跨越小台阶 / 不可通行高台阶或落差”。
3. 引入现有相机作为近距离和外观信息补充：L1 负责空间几何与距离，相机负责近场盲区、边缘连续性和视觉类别辅助。
4. 先输出独立的台阶/障碍检测结果及可视化证据；检测稳定后，再决定如何接入 costmap 或底盘通行决策。

### 约束

- Point-LIO 继续只订阅原始 `/unilidar/cloud` + `/unilidar/imu`，不把相机结果或 `/unilidar/cloud_aligned` 塞回里程计输入。
- L1 内置 IMU 继续用于 Point-LIO；相机是感知互补，不替代当前已跑通的 LIO 链路。
- 台阶识别与导航分开验收：先证明“识别对”，再证明“车能据此安全决策”。
- 近距离安全不能只依赖 L1；底盘实走阶段保留急停，并根据盲区情况评估相机、保险杠或其他近场传感器。

控制链路保持解耦：

- L1 只负责感知。
- `/cmd_vel` 只负责控制命令。
- 不把控制命令反推成位姿或里程计。
