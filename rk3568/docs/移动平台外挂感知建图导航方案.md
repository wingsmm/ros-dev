# 移动平台外挂感知建图导航方案

## 1. 目标

本方案记录后续方向：做一套可迁移的外挂感知、建图和导航能力。

当前 `xtark` 小车主要作为学习和验证平台；公司自研小车平台是后续目标接入对象。方案设计不绑定某一台小车，也不预设必须改动底盘控制板。

## 2. 当前硬件基础

已验证或计划纳入的传感器：

| 类型 | 说明 |
|------|------|
| 2D 雷达 | RPLidar，用于 `/scan`、2D 建图和定位 |
| 深度相机 | Astra 或同类深度摄像头，用于深度图、点云和避障试验 |
| 3D 雷达 | 语树 L1，用于后续 3D 感知、点云建图或障碍物检测 |
| 采集盒 | RK3568 已完成传感器采集验证，负责贴近 USB 传感器 |
| 开发计算 | PC 用于建图、可视化、算法验证和开发调试 |
| 最终主机 | 后续可迁移到 RK3588、Jetson 或其他更强车载主机 |

## 3. 角色定位

```text
外挂感知盒
  ├─ 采集雷达 / 相机 / IMU 等传感器
  ├─ 发布 ROS2 topic
  ├─ 运行建图、定位、避障和导航决策
  └─ 输出速度目标给底盘

小车底盘平台
  ├─ 负责运动控制
  ├─ 接收速度目标并驱动电机
  └─ 反馈实际运动状态
```

核心边界：

```text
RK -> 底盘：/cmd_vel 或等价速度指令
底盘 -> RK：/odom_base 或等价速度 / 位移反馈
```

RK 负责“看环境、建地图、定位、规划、告诉车怎么走”；底盘负责“按指令让轮子动，并告诉 RK 实际走了多少”。公司小车如果不是 ROS 接口，需要做一层适配：把 `/cmd_vel` 转成底盘协议，把底盘反馈转成 `/odom_base`。

RK3568 当前更适合作为稳定的传感器采集节点；开发阶段把复杂视觉、3D 点云、建图、导航规划和 RViz 放到 PC 上。方案稳定后，再决定是否迁移到 RK3588、Jetson 或其他强主机。

开发阶段原则：

```text
USB 传感器 -> RK3568
ROS2 topic -> PC
算法 / RViz / Nav2 -> PC
```

VM / PC 不直接碰 USB 传感器，避免 USB 透传、UVC、设备枚举和实时性问题。

## 4. 开发方式

现阶段采用“PC 控制开发 + 小车驮着 RK3568 跑”的方式：

```text
PC
  ├─ 作为开发台和控制台
  ├─ 运行 RViz、建图、导航调试和参数调整
  └─ 订阅 RK3568 发布的 ROS2 topic

RK3568
  ├─ 跟随小车移动
  ├─ 直接连接 RPLidar、深度相机、后续 3D 雷达 / IMU
  └─ 稳定发布 /scan、/camera/*、/points、/imu 等 topic

xtark 或其他小车平台
  ├─ 作为运动平台
  ├─ 驮着 RK3568 和传感器移动
  └─ 后续接收速度指令并反馈实际运动
```

开发阶段可以先让小车通过原有方式遥控移动，PC 只负责订阅传感器数据、建图、可视化和算法验证。进入闭环导航阶段后，再接入底盘的速度指令和运动反馈接口。

## 5. 分阶段思路

| 阶段 | 目标 |
|------|------|
| 阶段 1 | RK3568 稳定发布 `/scan`、`/camera/*` 等传感器 topic |
| 阶段 2 | PC 订阅 RK3568 发布的 ROS2 topic，验证建图、RViz、地图保存 |
| 阶段 3 | 接入公司小车底盘的 `/cmd_vel` 和 `/odom_base` 或等价接口 |
| 阶段 4 | 在 PC 上运行定位、Nav2、自主导航和避障策略验证 |
| 阶段 5 | 方案稳定后迁移到 RK3588、Jetson 或其他强主机 |

## 6. 关键判断

- 只有雷达和相机，可以做建图试验，但不能完整闭环自主导航。
- 自主导航至少需要两个底盘接口：RK 发速度目标，底盘反馈实际运动。
- IMU 可以辅助姿态和短期运动估计，但不能替代底盘里程计。
- GPS / RTK 只适合室外定位场景，室内建图导航不作为优先依赖。
- 语树 L1 和深度相机更适合放到后续感知增强阶段，不影响先用 2D 雷达跑通建图链路。
- PC 开发阶段能绕开 RK3568 算力不足问题；RK3568 只承担传感器采集和 topic 发布。
- 网络带宽需要按需控制，建图优先使用 `/scan`，深度图和点云按试验需要开启。

## 7. 待讨论问题

| 问题 | 说明 |
|------|------|
| 公司小车底盘接口 | 是否提供 ROS topic、串口协议、CAN、网络 API 或其他控制接口 |
| 控制入口 | 是否能接收 `/cmd_vel`，或需要适配成底盘私有速度指令 |
| 运动反馈 | 是否能输出 `/odom_base`，或编码器速度 / 位移反馈 |
| 传感器安装位 | 2D 雷达、3D 雷达、深度相机相对 `base_link` 的 TF 需要实测 |
| 算力分配 | 哪些运行在 RK3568，哪些迁移到 RK3588、Jetson 或 PC |
| ROS 版本边界 | 公司平台使用 ROS1、ROS2，或需要桥接 |
| 网络带宽 | `/camera/*`、点云、3D 雷达数据是否需要压缩、降频或分流 |

## 8. 当前结论

短期先把 RK3568 固化为外挂传感器采集盒；开发阶段用 PC 订阅 RK3568 的 ROS2 topic，完成建图、可视化、导航和算法验证；长期再根据公司小车底盘接口，接入“速度指令 + 运动反馈”，并把稳定后的方案迁移到 RK3588、Jetson 或其他强主机。
